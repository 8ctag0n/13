┃ RIESGOS Y MITIGACIONES                                                      ┃
┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┛

🔴 RIESGO ALTO: Circuito no genera proofs válidos después de múltiples intentos
   ├─ Impacto: Bloqueador total del proyecto
   ├─ Probabilidad: Media (circuito complejo con 228K constraints)
   ├─ Mitigación:
   │   1. Crear circuito P1 ultra-simple (2 constraints)
   │   2. Validar manualmente cada hash Poseidon
   │   3. Consultar expertos Circom si >4h stuck
   └─ Contingencia: Mock verification para demo (deshabilitar pairing check)

🔴 RIESGO ALTO: Performance de verificación inaceptable (>5s por proof)
   ├─ Impacto: UX malo, no escalable
   ├─ Probabilidad: Baja (Groth16 es rápido, ~1-5ms esperado)
   ├─ Mitigación:
   │   1. Benchmark con PreparedVK (ya implementado)
   │   2. Caché de VKs en memoria
   └─ Contingencia: Async verification + webhook callback

🟡 RIESGO MEDIO: VK no carga por formato incorrecto
   ├─ Impacto: No verifica proofs
   ├─ Probabilidad: Baja (formato snarkjs estandarizado)
   ├─ Mitigación:
   │   1. Validar JSON con jq antes de cargar
   │   2. Unit tests de AttestationService
   └─ Contingencia: Backward compatible mode (acepta sin verificar)

🟡 RIESGO MEDIO: E2E test falla por issues de infraestructura
   ├─ Impacto: No podemos validar sistema
   ├─ Probabilidad: Media
   ├─ Mitigación:
   │   1. PHASE 0 valida todo antes de empezar
   │   2. Health checks en docker-compose
   └─ Contingencia: Test manual con curl
